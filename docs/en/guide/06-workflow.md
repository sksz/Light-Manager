## The order you keep to

```
make check-env  →  make install  →  work  →  make qa  →  [benchmark]  →  documentation
```

The last step is not an ornament and is not put off: **a step that changes
a key, a setting, a command, a query or a module updates the manual and the
guide in the same step.** A documentation debt with no owner is a debt nobody
will ever pay.

## Three rules that are hard in this project

1. **The entry point to a process is a `make` target.** `make` with no arguments
   prints the list; a target that is not in that list does not exist. Where the
   project has **its own tool** (`bin/render-bench`, `bin/terminal-probe`), you
   use that one rather than improvising a substitute. Narrowing a run may be
   called directly — a single test by filter, a single benchmark axis; **what is
   forbidden is a parallel road to a process that already has an entry point**.
2. **Before a benchmark and before looking at a frame you ask for the machine to
   be freed** — and wait for confirmation. A loaded host produces a spread at
   which `--save` refuses to write a baseline, and numbers from such a run are no
   use as a reference point.
3. **Golden frames are refreshed only after reading the diff.** A file
   regenerated by a machine stops being a test.

## Environment and installation

```bash
make check-env   # can this machine carry the project — works before installing
make install     # composer install; repeated it does nothing
```

`make check-env` distinguishes **hard** requirements (they end with an error
code), **warnings** (a missing `SIXEL` coder) and **information** (`glfw`,
`intl`, `xterm`). One thing it cannot check and says so plainly: whether the
terminal itself speaks Sixel — that is what `make probe` is for.

## The quality gate

```bash
make qa            # cs-check → stan → test, stopping at the first failure
make qa-full       # the same to the end, with a summary
make cs-check      # PHP-CS-Fixer — a preview of changes, no writing
make cs            # PHP-CS-Fixer — write the fixes
make stan          # PHPStan (level max)
make test          # PHPUnit — both groups at once
make coverage      # coverage into build/coverage/ (needs Xdebug or PCOV)
```

The definitions of these commands live in `composer.json` (`cs`, `cs:check`,
`stan`, `test`) — the `make` targets **call them rather than repeat them**. The
Makefile is a thin layer, not a second source of truth.

**PHPStan has run at level `max` since the start of the project.** Instead of
lowering the level globally you use pointed, justified `@phpstan-ignore`. The
analysis covers `src`, `tests`, `lang` and `examples`.

## Tests

```bash
make test-unit                             # classes
make test-functional                       # user flows
make test ARGS='--filter TreeStateTest'    # narrowing goes the same road
```

**A functional flow** is a named sequence of keys through `ScreenFixture` — the
full set of screens and **real modules** without the filesystem, the terminal
and Imagick — with assertions at checkpoints. Application startup and window
resizing additionally go through `GameLoop` with `ScriptedTerminal`, because
a tick cannot be checked without the loop.

The `tests/Functional/` directory is **a catalogue of behaviours**, not
a collection of side effects of successive steps: **a missing flow in the
catalogue is a gap to fill, not a natural state**.

**No test calls a real `ssh`, `sftp`, `kubectl` or `docker`** — and that is
a criterion, not a convenience. The ports for those have stubs in
`tests/Support/`.

**Golden frames** (`tests/Golden/`) are a serialization of the primitives of
`ScenarioFactory` frames, compared independently of the renderer. They are
refreshed **only** by `./bin/render-bench --golden-save`, after reading the diff.

## Watching terminal input

```bash
make probe         # ./bin/terminal-probe
make probe-xterm   # the same in XTerm with the graphics-mode resources
```

At startup it shows the detected rendering mode, then prints the name of each
key and its bytes, one line per event. **Mouse events show up the same way** —
and that is the only way to check whether an incomplete sequence waits for the
rest or falls apart into separate characters. To leave: `q` or `Ctrl`+`C`.

## Benchmarking

Benchmarking has **its own entry points** and **its own document**: the axes,
the baselines, the regression thresholds and the catalogue of scenarios are
described in [`docs/pomiary/README.md`](../../pomiary/README.md). Here only what
concerns the order of work.

```bash
make bench          # the Sixel path
make bench-window   # the windowed path (OpenGL, hidden window)
make bench-text     # the text path (ANSI)
make bench-loop     # the loop tick — input, state, frame composition, no renderer
make bench-xterm    # under a real XTerm — the only road to --transfer
```

**When you benchmark:** when a step touches the **frame path** — drawing,
primitives, quantization, encoding or the loop tick. A step that adds a command,
a query or a setting has nothing to measure and does not pretend otherwise.

**Before you measure — ask for the machine to be freed and wait for
confirmation.** The benchmark targets have no technical barrier; they have this
rule.

**A gap worth knowing:** the module tick is **measured by none of the four
axes**. The Sixel, windowed and text ones measure drawing, and `--loop` measures
the loop **without modules**. The cost of talking to a daemon, a registry and
a cluster is accounted for today by reasoning, not by a number — that is
a measurement debt of the project, named in step 61.

## Building a distribution

```bash
make build
```

The result is **two things in the `build/` directory**: the archive
`light-manager-<version>.phar` (the version from the `version` field in
`composer.json`) and an `assets/` directory **next to** it. The archive carries
`src/`, `lang/`, `bin/light-manager` and the dependencies without the dev ones,
with a classmap autoloader; `tests/`, `docs/`, `examples/` and the repository
tools do not go into it. The build ends by checking that the result loads.

**The assets sit next to the archive for a reason worth knowing**: the `GL\Audio`
engine is a C extension and will not read a file from under `phar://`. In a built
application a track is therefore added to the playlist by **absolute path**.

Cleaning up: `make clean` removes `build/` and the tools' artefacts,
`make dist-clean` adds `vendor/`. Neither touches `docs/pomiary/` nor the
configuration in `HOME`.

## The changelog and the plan

A finished step is added to [`CHANGELOG.md`](../../../CHANGELOG.md) according to
the [changelog convention](../../konwencja-changelogu.md) — provided it gave the
user something visible. The numbering runs `phase.step.fix`, and **release names
and numbers are never invented single-handedly**.

Step statuses, the dependency graph and the list that closes a step live in
[`docs/plans/00-index.md`](../../plans/00-index.md), the "Śledzenie postępu"
chapter.
